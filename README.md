## АННОТАЦИЯ

UROBOROS_v1.0 — экспериментальная архитектура внешней памяти, предназначенная для исследования контекстно-зависимых ассоциаций между сохранёнными событиями, знаниями и информационными состояниями искусственного агента.

В отличие от простых систем хранения и семантического извлечения, архитектура рассматривает ассоциацию не как неизменную связь между двумя объектами, а как **условное отношение**, вероятность проявления которого зависит от текущего контекста и накопленных свидетельств.

Центральный механизм системы — **Memory Boundary Learning (MBL)**: обучение границ применимости ассоциативных связей.

**Дополнительные механизмы:**

- **Trace Preservation** — сохранение происхождения исходных воспоминаний.
- **Potential Association Generation** — формирование неподтверждённых ассоциативных гипотез.
- **Contextual Association Modeling** — моделирование зависимости ассоциаций от контекста.
- **Active Context Probing** — выбор информативных контекстов для проверки гипотез.
- **Negative Association Traces** — сохранение отрицательных результатов проверок.
- **Conflict Branch Preservation** — сохранение конкурирующих версий воспоминаний.
- **Dual Exploration** — сочетание целевого и исследовательского поиска.
- **Retrieval Route Reconfiguration** — адаптация маршрутов извлечения информации.

UROBOROS **не предполагает** наличия сознания, биологических нейронов или субъективных переживаний у языковой модели. Архитектура описывает вычислительные механизмы внешней памяти и наблюдаемое поведение системы.

## 1. ИСХОДНАЯ ПРОБЛЕМА

### 1.1. Ограничения традиционного подхода

Большинство практических архитектур внешней памяти для LLM-агентов используют комбинацию следующих механизмов:

1. Сохранение сообщений и событий.
2. Семантическое индексирование.
3. Поиск по сходству.
4. Извлечение релевантных фрагментов.
5. Обновление или обобщение сохранённой информации.

Такая архитектура позволяет возвращать ранее полученные сведения, но сама по себе не гарантирует корректного понимания условий, при которых определённая информация должна быть активирована.

Например, два события могут иметь высокое семантическое сходство, но относиться к совершенно разным обстоятельствам.

Обратная ситуация также возможна: два воспоминания могут иметь низкое смысловое сходство, но быть тесно связаны через общий сенсорный, временной или ситуационный контекст.

Следовательно:

> **Семантическая близость не равна контекстной применимости.**

### 1.2. Основная исследовательская гипотеза

Если ассоциация между двумя воспоминаниями зависит от контекста, то система должна хранить и обновлять модель этой зависимости.

Предлагается перейти от представления:

```text
MEMORY A ↔ MEMORY B
```

к представлению:

```text
MEMORY A ↔ MEMORY B | CONTEXT C
```

При этом система должна учитывать не только успешные активации, но и корректно проведённые проверки, в которых ожидаемая связь **не проявилась**.

### 1.3. Исходные принципы HALVITA

Архитектура формализует три исходные исследовательские идеи.

**Принцип I. Ассоциативное происхождение воспоминаний.**

Воспоминания могут активироваться через косвенные признаки: запахи, звуки, изображения, временные обстоятельства, смысловые категории и другие элементы контекста.

**Принцип II. Сохранение противоречий.**

Конкурирующие версии воспоминаний не должны автоматически уничтожать друг друга. Их происхождение, контекст и свидетельства необходимо сохранять отдельно.

**Принцип III. Запоминание потенциальных связей.**

Система должна хранить не только установленные ассоциации, но и потенциальные отношения, которые ещё требуют проверки.

В UROBOROS эти принципы переводятся в вычислительные операции.

## 3. ОБЩАЯ АРХИТЕКТУРА

### 3.1. Четыре основных уровня

UROBOROS организован вокруг четырёх логических уровней.

#### L1 — TRACE MEMORY

Хранение исходных событий и их происхождения.

Каждая запись содержит:

- уникальный идентификатор;
- исходное содержание;
- источник информации;
- время получения;
- первоначальный контекст;
- тип события;
- ссылки на исходное свидетельство;
- статус достоверности.

Исходная запись является **неизменяемой** в рамках обычного цикла обновления.

#### L2 — ASSOCIATIVE MEMORY

Граф обнаруженных отношений между воспоминаниями.

Объекты графа — воспоминания и события.

Связи могут отражать:

- временное соседство;
- семантическое сходство;
- общие признаки;
- подтверждённую ассоциацию;
- предполагаемую зависимость;
- конфликт или несовместимость;
- причинную гипотезу, если она отдельно проверяется.

> Наличие ребра не означает доказанную причинность.

#### L3 — POTENTIAL MEMORY

Хранение неподтверждённых ассоциативных гипотез.

Потенциальная связь содержит:

- исходные узлы;
- предполагаемый тип отношения;
- контекст появления гипотезы;
- альтернативные объяснения;
- текущую оценку уверенности;
- статус проверки;
- приоритет дальнейшего исследования.

Потенциальные связи не должны автоматически использоваться как установленные факты.

#### L4 — BOUNDARY MEMORY

Хранение контекстов применимости и неприменимости ассоциаций.

Для каждой проверяемой связи сохраняются:

- контексты успешного проявления;
- контексты отсутствия ожидаемого проявления;
- неопределённые результаты;
- качество проведённых проверок;
- оценка неопределённости модели;
- версия модели, на которой получены результаты.

Этот уровень обеспечивает центральный механизм **Memory Boundary Learning**.

### 3.2. Общая схема

```text
              INPUT / EXPERIENCE
                      |
                      v
              [ TRACE MEMORY ]
                      |
                      v
             [ ASSOCIATIVE GRAPH ]
                      |
                      v
              [ POTENTIAL MEMORY ]
                      |
                      v
             [ CONTEXTUAL MODEL ]
                      |
                      v
              [ ACTIVE PROBING ]
                      |
                      v
              [ BOUNDARY MEMORY ]
                      |
                      v
            [ MEMORY RECONFIGURATION ]
                      |
                      +---------> NEXT CYCLE
```

### 3.3. Общая модель

Пусть:

- **E** — множество исходных событий;
- **G** — ассоциативный граф;
- **P** — множество потенциальных связей;
- **B** — множество моделей границ применимости;
- **C** — пространство контекстов;
- **X** — множество накопленных свидетельств.

Тогда архитектура представляется как:

```text
UROBOROS = {E, G, P, B, X}
```

Полное состояние системы:

```text
S(t) = {E(t), G(t), P(t), B(t), X(t)}
```

Переход:

```text
S(t+1) = F(S(t), input(t), budget(t))
```

Это формальная модель состояния внешней памяти, а не модель внутренних состояний сознания.

## 4. TRACE MEMORY — СОХРАНЕНИЕ ПРОИСХОЖДЕНИЯ

### 4.1. Принцип Trace Preservation

Исходные данные должны сохраняться отдельно от последующих интерпретаций.

Если система изменила оценку события, это не должно приводить к изменению первоначальной записи.

**Пример:**

Первоначальная запись:

> «Событие произошло вечером».

Позднее появилась другая информация:

> «Возможно, событие произошло утром».

Система создаёт новое свидетельство и обновляет текущую интерпретацию, но **не переписывает** исходную запись.

Формула:

```text
SOURCE RECORD ≠ CURRENT INTERPRETATION
```

### 4.2. Структура события

```json
{
  "id": "M-001",
  "content": "Original memory content",
  "source": {
    "type": "user_report",
    "reference": "SOURCE-001"
  },
  "timestamp": "T1",
  "context": {
    "sensory": [],
    "temporal": {},
    "situational": {},
    "semantic": [],
    "history": []
  },
  "provenance_status": "preserved",
  "version": 1
}
```

Это пример структуры, а не обязательная схема окончательной базы данных.

### 4.3. Правило неизменяемости

Любое изменение должно оформляться отдельным событием журнала.

```text
NEW EVIDENCE → NEW RECORD → UPDATED INTERPRETATION
```

Удаление, исправление или аннулирование данных должно происходить через явную операцию с аудитом, а не через скрытую перезапись.

## 5. ASSOCIATIVE MEMORY — ГРАФ СВЯЗЕЙ

### 5.1. Формальная структура

Ассоциативная память представляется ориентированным или неориентированным мультиграфом:

```text
G = (V, A)
```

Где:

- **V** — множество узлов памяти;
- **A** — множество ассоциативных отношений.

Для каждой связи:

```text
a_ij = (M_i, M_j, type, evidence, status)
```

**Возможные типы связей:**

| Тип | Значение |
|---|---|
| `SEMANTIC` | Смысловое сходство |
| `TEMPORAL` | Временная близость |
| `SENSORY` | Сенсорная ассоциация |
| `SITUATIONAL` | Общая ситуация |
| `CAUSAL_HYPOTHESIS` | Предполагаемая причинная связь |
| `CONTRADICTION` | Противоречие |
| `CONTEXTUAL` | Контекстно-зависимая ассоциация |

Система не должна автоматически превращать совместное появление событий в причинную связь.

### 5.2. Контекст как самостоятельная переменная

Для каждого события создаётся вектор контекста:

```text
x = φ(C)
```

Он может включать:

- сенсорные признаки;
- временные признаки;
- ситуационные признаки;
- семантические признаки;
- признаки предыдущей истории;
- идентификаторы контекстного состояния;
- источник и качество данных.

Вектор может строиться из категориальных признаков, числовых параметров или эмбеддингов.

> **Важно:** контекст не обязательно должен быть полностью известен. Отсутствующие признаки маркируются как **неизвестные**, а не автоматически принимаются за нулевые.

## 6. POTENTIAL ASSOCIATION GENERATION

### 6.1. Формирование потенциальных связей

При появлении нового события система извлекает релевантные воспоминания и формирует кандидатов на ассоциативную связь.

**Источники кандидатов:**

1. Семантическое сходство.
2. Общие сенсорные признаки.
3. Временные совпадения.
4. Ситуационная близость.
5. Повторяющиеся маршруты активации.
6. Обнаруженные структурные закономерности.

**Каждая потенциальная связь получает статус:**

- `CANDIDATE` — создана;
- `PENDING` — ожидает проверки;
- `SUPPORTED` — имеет положительные свидетельства;
- `LIMITED` — имеет подтверждённые контекстные ограничения;
- `REJECTED` — отвергнута в заданной области применения;
- `INCONCLUSIVE` — данных недостаточно.

> Отвергнутая связь **не должна автоматически удаляться** из истории.

### 6.2. Разделение факта и гипотезы

**Пример:**

**Факт:**

> «События A и B были сохранены в одной временной последовательности».

**Гипотеза:**

> «Событие A может активировать воспоминание B».

**Вывод:**

> «Связь A → B наблюдалась в контексте C».

Эти три утверждения имеют **разный эпистемический статус**.

UROBOROS обязан хранить это различие.

## 7. CONTEXTUAL ASSOCIATION MODELING

### 7.1. Основная математическая модель

Для пары воспоминаний M_i и M_j вводится условная вероятность применимости связи:

```text
p_ij(C) = P(Y_ij = 1 | C, E)
```

Где:

- **Y_ij** — результат проверки связи;
- **C** — контекст проверки;
- **E** — накопленные свидетельства.

В простейшей версии используется логистическая модель:

```text
p_ij(C) = σ(θ_ijᵀ φ(C))
```

Где:

- **θ_ij** — параметры конкретной связи;
- **φ(C)** — признаки контекста;
- **σ(z) = 1 / (1 + exp(-z))**.

Данная модель является **стартовым приближением**. Она предполагает, что зависимость можно достаточно хорошо описать выбранными признаками и линейной комбинацией перед логистической функцией.

Для более сложных зависимостей в последующих версиях можно использовать:

- Bayesian Logistic Regression;
- Gaussian Processes;
- деревья решений;
- нелинейные модели;
- контекстные модели с несколькими латентными состояниями.

### 7.2. Обновление модели

Для валидного бинарного наблюдения:

```text
θ(t+1) = θ(t) + η (y - p) φ(C)
```

Где:

- **y = 1** — связь проявилась;
- **y = 0** — связь не проявилась;
- **p** — предсказанная вероятность;
- **η** — скорость обновления.

Для неопределённого результата обновление **не производится**.

При этом важно учитывать качество наблюдения и возможность того, что сама процедура извлечения памяти дала сбой.

### 7.3. Контекстная граница

Область применимости связи:

```text
B_ij = {C : p_ij(C) ≥ τ}
```

Где **τ** — выбранный порог активации.

Однако одной вероятности недостаточно. Модель может быть уверенной в ситуации, которую она почти не наблюдала.

Поэтому вводится дополнительное ограничение:

```text
B*_ij = {C : p_ij(C) ≥ τ AND U_ij(C) ≤ ε}
```

Где **U** — оценка неопределённости модели.

Таким образом, связь считается **надёжно применимой** только тогда, когда:

1. Вероятность её проявления достаточно высока.
2. Неопределённость оценки достаточно мала.

Это позволяет отделить высокую вероятность от высокой достоверности.

## 8. MEMORY BOUNDARY LEARNING

### 8.1. Центральный механизм UROBOROS

**Memory Boundary Learning** — механизм обучения границ применимости ассоциативных связей.

Его задача — определять, в каких контекстах связь подтверждается, в каких не проявляется, а в каких данных недостаточно.

Система хранит не только итоговую оценку ассоциации, но и **историю проверок**.

### 8.2. Три класса свидетельств

**POSITIVE TRACE — C+**

Связь проявилась при валидной проверке.

**NEGATIVE TRACE — C-**

Связь не проявилась при валидной проверке, несмотря на наличие достаточных условий для обнаружения.

**INCONCLUSIVE TRACE — C?**

Результат невозможно достоверно интерпретировать.

**Примеры причин неопределённости:**

- неполный контекст;
- сбой извлечения;
- недостаточное качество исходных данных;
- неоднозначная процедура проверки;
- отсутствие независимой оценки результата.

### 8.3. Важнейшее разграничение

Необходимо различать:

```text
ASSOCIATION NOT OBSERVED
```

и

```text
ASSOCIATION DOES NOT EXIST
```

**Первое** — наблюдение.

**Второе** — гораздо более сильное утверждение, которое нельзя выводить из одного неудачного извлечения.

Отрицательное свидетельство ограничивает конкретную гипотезу в конкретных условиях, но не уничтожает исходные воспоминания.

### 8.4. Negative Association Trace (NAT)

Каждая отрицательная проверка сохраняется отдельной записью:

```json
{
  "id": "NAT-001",
  "memory_pair": ["M-001", "M-014"],
  "tested_context": "C-003",
  "expected": "association_active",
  "observed": "association_not_observed",
  "test_validity": true,
  "retrieval_success": true,
  "evidence_quality": 0.9,
  "result": "negative",
  "model_version": "1.0"
}
```

> Числовая оценка качества здесь условная.

NAT — не просто отрицательная оценка связи. Это свидетельство о результате конкретного **эксперимента**.

## 9. ACTIVE CONTEXT PROBING

### 9.1. Основная задача

UROBOROS не ограничивается пассивным ожиданием новых контекстов.

Если потенциальная связь недостаточно изучена, система может выбрать контекст для дополнительной проверки.

Цель — получить максимально **информативное** наблюдение при ограниченном вычислительном бюджете.

### 9.2. Конкурирующие гипотезы

**Пример:**

- **H1:** воспоминание активируется из-за сенсорного сходства.
- **H2:** воспоминание активируется из-за семантической категории.
- **H3:** связь возникает только при совместном наличии обоих признаков.

Вместо того чтобы просто повторять прежнюю проверку, система выбирает условия, которые позволят **различить** гипотезы.

### 9.3. Выбор информативного контекста

Формула:

```text
C* = argmax_C E[H(H|E) - H(H|E,o,C)]
```

Где:

- **H** — набор конкурирующих гипотез;
- **E** — накопленные свидетельства;
- **o** — возможный результат теста;
- **H(·)** — энтропия;
- **C*** — контекст, ожидаемо уменьшающий неопределённость.

Это вариант критерия ожидаемого прироста информации.

### 9.4. Защита от ложного исследования

Синтетический контекст, сгенерированный самой LLM, **не должен** считаться независимым подтверждением реальной связи.

Необходимо различать:

- реальные пользовательские наблюдения;
- контролируемые тесты;
- симулированные тесты;
- модельные предположения;
- автоматически сгенерированные сценарии.

Результаты каждого типа имеют собственный статус доказательности.

> Активные проверки личных воспоминаний или чувствительных данных не должны проводиться без соответствующего разрешения пользователя.

## 10. DUAL EXPLORATION

UROBOROS использует два режима исследования.

### 10.1. Directed Exploration

Целевое исследование ради конкретной задачи.

**Пример:** поиск информации, необходимой для ответа или выполнения действия.

Главная переменная — ожидаемая полезность для текущей задачи.

### 10.2. Open Exploration

Исследовательский поиск без немедленной практической выгоды.

**Пример:** поиск повторяющихся структур между ранее не связанными событиями.

Главная переменная — ожидаемая информативность.

### 10.3. Общая функция выбора

```text
S(C) = αT(C) + βI(C) + γN(C) - λK(C) - μR(C)
```

Где:

- **T** — ожидаемая ценность для задачи;
- **I** — ожидаемый информационный прирост;
- **N** — новизна контекста;
- **K** — вычислительная стоимость;
- **R** — риск ложного вывода;
- **α, β, γ, λ, μ** — настраиваемые коэффициенты.

Выбор контекста должен учитывать общий бюджет исследования.

Система не обязана проверять каждую потенциальную связь.

При недостаточном бюджете она сохраняет гипотезу в очереди.

---

## 11. CONFLICT BRANCH PRESERVATION

### 11.1. Проблема противоречий

При накоплении воспоминаний могут возникать несовместимые версии событий.

Автоматическое слияние таких записей способно уничтожить важную информацию.

UROBOROS использует **ветвление конфликтов**.

### 11.2. Структура

```text
             CONFLICT NODE
                   |
          +--------+--------+
          |                 |
       BRANCH A          BRANCH B
          |                 |
       SOURCE A          SOURCE B
          |                 |
       CONTEXT A         CONTEXT B
          |                 |
       EVIDENCE A        EVIDENCE B
          |                 |
          +--------+--------+
                   |
             CURRENT STANCE
```

**Каждая ветвь сохраняет:**

- первоначальный источник;
- собственный контекст;
- историю подтверждений;
- историю опровержений;
- степень неопределённости;
- текущий статус.

### 11.3. Правило интерпретации

```text
UPDATE INTERPRETATION ≠ REWRITE HISTORY
```

Новые свидетельства могут изменить текущую рабочую версию.

Они **не должны автоматически уничтожать** историю предыдущих интерпретаций.

Текущая позиция агента — рабочая гипотеза, а не гарантированно объективная истина.

---

## 12. RETRIEVAL ROUTE RECONFIGURATION

После накопления свидетельств система может корректировать способы извлечения памяти.

**Например:**

Если ассоциация подтверждается при сенсорном контексте, система может повысить приоритет соответствующего маршрута извлечения именно при наличии этого признака.

Если ассоциация неоднократно не подтверждается в определённом контексте, система может уменьшить её приоритет в аналогичных ситуациях.

Однако исходная связь **не удаляется** только из-за снижения приоритета.

**Необходимо разделять:**

- существование записи;
- существование ассоциации;
- вероятность её применимости;
- приоритет извлечения;
- актуальную уверенность.

Это разные характеристики.

### 12.1. Условная маршрутизация

Для каждого кандидата:

```text
R_ij(C) = p_ij(C) × confidence_ij(C) × relevance_ij(C)
```

Это простая стартовая функция ранжирования, а не универсальная формула оптимального поиска.

Позднее она может учитывать стоимость извлечения, риск ошибки и тип задачи.

## 13. ПОЛНЫЙ АЛГОРИТМ UROBOROS_v1.0

### 13.1. Этапы обработки

1. **ENCODE** — сохранить новое событие.
2. **VALIDATE** — проверить источник и полноту данных.
3. **ACTIVATE** — извлечь релевантные воспоминания.
4. **GENERATE** — создать потенциальные связи.
5. **CLASSIFY** — определить статус гипотез.
6. **SELECT** — выбрать приоритетные проверки.
7. **PROBE** — выполнить проверку в допустимом контексте.
8. **EVALUATE** — оценить валидность результата.
9. **TRACE** — сохранить свидетельство.
10. **UPDATE** — обновить контекстную модель.
11. **PRESERVE** — сохранить конфликтующие версии.
12. **RECONFIGURE** — обновить маршруты извлечения.
13. **AUDIT** — записать изменения в журнал.

### 13.2. Псевдокод

```python
def UROBOROS_v1(experience, memory, budget):

    # 1. Encode source event
    trace = encode_with_provenance(experience)

    # 2. Validate source
    if not validate_trace(trace):
        return memory.store_quarantine(trace)

    # 3. Preserve original record
    memory.store_immutable(trace)

    # 4. Retrieve relevant memories
    active = memory.retrieve_by_context(trace)

    # 5. Generate candidate associations
    candidates = generate_potential_links(
        trace,
        active,
        memory.association_graph
    )

    # 6. Evaluate each candidate
    for link in candidates:

        model = memory.get_context_model(link)

        prediction = model.predict(trace.context)

        # Avoid redundant tests when evidence is sufficient
        if prediction.is_reliable:
            continue

        # Generate alternative explanations
        hypotheses = generate_competing_hypotheses(link)

        # Select informative context
        probe = select_discriminating_context(
            hypotheses=hypotheses,
            task_value=True,
            information_gain=True,
            budget=budget
        )

        if probe is None:
            memory.queue_for_future(link)
            continue

        # Run only authorized and valid tests
        result = evaluate_association(
            link=link,
            context=probe
        )

        # Preserve the test outcome
        if result.valid:

            memory.store_evidence(
                link=link,
                context=probe,
                result=result
            )

            model.update(
                context=probe,
                outcome=result.label
            )

        else:

            memory.store_inconclusive(
                link=link,
                context=probe,
                result=result
            )

    # 7. Preserve contradictory branches
    memory.preserve_conflict_branches()

    # 8. Update contextual applicability
    memory.update_context_boundaries()

    # 9. Rebuild retrieval priorities
    memory.update_retrieval_routes()

    # 10. Audit
    memory.write_audit_log()

    return memory
```

> Псевдокод описывает логику архитектуры. Он не является готовым исполняемым модулем без реализации перечисленных функций.

## 15. МАТЕМАТИЧЕСКОЕ ЯДРО

Ниже приведён компактный набор формул, определяющих начальную версию.

### 15.1. Контекстная вероятность

```text
P_ij(C) = σ(θ_ijᵀ φ(C))
```

### 15.2. Обновление параметров

```text
θ' = θ + η(y - P)φ(C)
```

### 15.3. Область применимости

```text
B_ij = {C : P_ij(C) ≥ τ}
```

### 15.4. Область надёжной применимости

```text
B*_ij = {C : P_ij(C) ≥ τ AND U_ij(C) ≤ ε}
```

### 15.5. Информационный прирост

```text
IG = H_before - E[H_after]
```

### 15.6. Выбор контекста

```text
C* = argmax_C [IG(C) - λ Cost(C) - μ Risk(C)]
```

### 15.7. Функция исследовательской полезности

```text
S(C) = αT + βI + γN - λK - μR
```

### 15.8. Состояние памяти

```text
S(t+1) = F(S(t), E(t), C(t), X(t))
```

### 15.9. Разделение исходной записи и интерпретации

```text
SOURCE(t) ≠ INTERPRETATION(t)
```

### 15.10. Полный принцип архитектуры

```text
MEMORY = TRACE + ASSOCIATION + POTENTIAL + BOUNDARY + EVIDENCE
```

## 16. ЭКСПЕРИМЕНТАЛЬНЫЙ ПРОТОКОЛ

### 16.1. Цель

Проверить, улучшает ли обучение границ применимости качество ассоциативного извлечения по сравнению с обычными подходами.

Эксперимент должен быть воспроизводимым и содержать заранее известную структуру истинных связей.

### 16.2. Синтетический набор данных

Создать несколько типов зависимостей:

**Тип A — сенсорная зависимость.**

Связь активируется при наличии определённого сенсорного признака.

**Тип B — временная зависимость.**

Связь зависит от временного состояния.

**Тип C — составная зависимость.**

Связь активируется только при совместном наличии двух или более условий.

**Тип D — ложная корреляция.**

События часто появляются рядом, но реальной зависимости между ними нет.

**Тип E — переключение контекста.**

Одна и та же пара событий имеет разные отношения в разных скрытых контекстных состояниях.

**Тип F — неполные наблюдения.**

Часть признаков отсутствует, поэтому система должна сохранять неопределённость.

### 16.3. Сравниваемые архитектуры

| Модель | Конфигурация |
|---|---|
| **BASE** | Обычная ассоциативная память |
| **A** | Нет отрицательных свидетельств |
| **B** | Нет активных контекстных проверок |
| **C** | Нет конкурирующих гипотез |
| **D** | Нет контекстных границ |
| **FULL** | Полный UROBOROS_v1 |

Каждая модель должна работать при **сопоставимом вычислительном бюджете**.

### 16.4. Метрики

**Boundary F1**

Оценка правильности определения области применимости ассоциации.

**False Activation Rate (FAR)**

Доля ложных активаций среди всех отрицательных случаев:

```text
FAR = FP / (FP + TN)
```

**Precision**

```text
Precision = TP / (TP + FP)
```

**Recall**

```text
Recall = TP / (TP + FN)
```

**Information Gain per Cost**

Количество полученной информации на единицу вычислительных затрат.

**Calibration Error**

Насколько заявленные вероятности соответствуют фактической частоте наблюдаемых результатов.

**Provenance Preservation**

Доля записей, у которых сохранено корректное происхождение.

**Conflict Preservation**

Доля исходных конфликтующих ветвей, сохранённых без незаметного слияния или потери истории.

### 16.5. Условия успешного эксперимента

UROBOROS должен:

1. Снижать число ложных активаций.
2. Корректно выявлять контекстные ограничения.
3. Сохранять исходные воспоминания.
4. Различать отрицательный и неопределённый результат.
5. Улучшать качество извлечения на новых контекстах.
6. Демонстрировать измеримый вклад активных проверок.
7. Не расходовать несоразмерно больше вычислительных ресурсов.

> Результаты необходимо оценивать на **отложенных данных**, которые не использовались при обучении контекстной модели.

## 17. АБЛЯЦИОННЫЕ ИССЛЕДОВАНИЯ

Чтобы определить реальный вклад каждого механизма, необходимо поочерёдно отключать компоненты.

### EXP-01 — Boundary Ablation

Отключить Memory Boundary Learning.

**Цель:** выяснить, насколько контекстные границы влияют на ложные активации.

### EXP-02 — Negative Trace Ablation

Отключить сохранение отрицательных свидетельств.

**Цель:** выяснить, теряет ли система способность учитывать контексты, в которых ассоциация не проявляется.

### EXP-03 — Active Probe Ablation

Отключить активный выбор контекста.

**Цель:** сравнить пассивное накопление наблюдений с целенаправленным исследованием.

### EXP-04 — Conflict Ablation

Отключить сохранение конкурирующих ветвей.

**Цель:** определить влияние автоматического разрешения противоречий на достоверность памяти.

### EXP-05 — Dual Exploration Ablation

Отключить свободный исследовательский режим.

**Цель:** измерить, какие закономерности система теряет при исключительно целевом поиске.

### EXP-06 — Context Uncertainty Ablation

Отключить оценку неопределённости.

**Цель:** проверить, не начинает ли система чрезмерно доверять малоизученным контекстам.

## 18. СРАВНЕНИЕ С СУЩЕСТВУЮЩИМИ НАПРАВЛЕНИЯМИ

UROBOROS разрабатывается не в вакууме. Его отдельные механизмы имеют аналоги в исследованиях памяти, контекстного обучения и LLM-агентов.

> Важно отделять уже известные решения от потенциального вклада новой архитектуры.

### 18.1. Контекстно-зависимое обучение

Исследования контекстно-зависимого обучения показывают, что формирование и использование памяти зависят от контекста, причём сам контекст может быть неопределённым.

**См.:**

Heald, Wolpert, Lengyel (2023). *The Computational and Neural Bases of Context-Dependent Learning.*
[https://doi.org/10.1146/annurev-neuro-092322-100402](https://doi.org/10.1146/annurev-neuro-092322-100402)

Это научная основа для рассмотрения контекста как самостоятельной переменной.

### 18.2. MRAgent

MRAgent использует ассоциативный граф **Cue–Tag–Content** и механизм активной реконструкции путей извлечения памяти.

**Сходство с UROBOROS:**

- ассоциативная структура;
- динамическое извлечение;
- активное исследование связей.

**Потенциальное различие:**

UROBOROS дополнительно делает предметом обучения **контекстную область применимости связи** и сохраняет отдельные отрицательные свидетельства о её проявлении.

**Публикация:**

Ji, Li, Hooi (2026). *Memory is Reconstructed, Not Retrieved: Graph Memory for LLM Agents.*
[https://proceedings.mlr.press/v306/ji26d.html](https://proceedings.mlr.press/v306/ji26d.html)

### 18.3. GAM

GAM использует иерархическую графовую память, разделяя развитие событий и тематические ассоциации.

**Сходство:**

- графовая организация;
- разделение типов памяти;
- управление долгосрочной структурой знаний.

**Потенциальное различие:**

В UROBOROS основной исследовательский объект — не только структура связей, но и **условия, при которых конкретная связь применима**.

**Публикация:**

*GAM: Hierarchical Graph-based Agentic Memory for LLM Agents* (ACL 2026).
[https://aclanthology.org/2026.acl-long.1600/](https://aclanthology.org/2026.acl-long.1600/)

### 18.4. MemCon

MemCon рассматривает управление памятью как адаптивный процесс и использует контекстную политику для выбора операций извлечения и обновления.

**Сходство:**

- контекстно-зависимое управление;
- исследование полезности операций;
- адаптивное распределение ресурсов.

**Потенциальное различие:**

UROBOROS исследует контекстную применимость отношений между конкретными воспоминаниями, а не только выбор операций управления памятью.

**Публикация:**

*Memory as a Controlled Process: Learned Adaptive Memory Management for LLM Agents* (2026).
[https://arxiv.org/abs/2607.13591](https://arxiv.org/abs/2607.13591)

### 18.5. RippleMem

RippleMem использует ассоциативное восстановление памяти и расширение поиска от найденных событийных якорей.

**Сходство:**

- ассоциативное извлечение;
- реконструкция связанных воспоминаний;
- работа с распределёнными свидетельствами.

**Потенциальное различие:**

UROBOROS ставит в центр исследование **границ применимости ассоциаций** и сохранение контекстных отрицательных результатов.

**Публикация:**

*RippleMem: From Isolated Retrieval to Associative Recollection for Long-Term Agent Memory* (2026).
[https://arxiv.org/abs/2608.13334](https://arxiv.org/abs/2608.13334)

### 18.6. Общий вывод сравнения

Ассоциативная память, контекстное обучение, активное исследование, адаптивное управление и сохранение истории уже являются известными направлениями.

Поэтому UROBOROS **нельзя обоснованно объявлять принципиально первым алгоритмом** такого типа без более широкого анализа литературы и экспериментального сравнения.

**Потенциальный исследовательский вклад:**

> **Единый цикл контекстного моделирования ассоциаций, активного выбора различающих проверок, сохранения отрицательных свидетельств и обучения области применимости конкретной связи.**

Именно эта комбинация должна стать предметом дальнейшей проверки на новизну и эффективности.

## 19. ОЖИДАЕМЫЕ ПРЕИМУЩЕСТВА И ОГРАНИЧЕНИЯ

### 19.1. Ожидаемые преимущества

- Снижение количества ложных ассоциаций.
- Более точное извлечение информации в изменяющихся контекстах.
- Сохранение исходных воспоминаний и происхождения.
- Более корректная работа с противоречиями.
- Возможность целенаправленно исследовать неизвестные связи.
- Разделение фактов, гипотез и результатов проверок.
- Аудируемая история изменений памяти.

> Это ожидаемые свойства, а не уже доказанные результаты.

### 19.2. Ограничения

**Проблема 1 — качество контекста.**

Если признаки контекста определены неправильно, модель будет учиться на некорректных данных.

**Проблема 2 — ложные отрицательные результаты.**

Неудачное извлечение может быть ошибочно принято за отсутствие ассоциации.

**Проблема 3 — вычислительная стоимость.**

Активные проверки требуют дополнительных операций и могут быть дорогими.

**Проблема 4 — переобучение.**

Система может запомнить конкретные тестовые контексты и плохо работать на новых.

**Проблема 5 — ложные закономерности.**

Повторяющиеся совпадения не доказывают причинность.

**Проблема 6 — накопление противоречий.**

Без управления памятью система может хранить чрезмерное количество конкурирующих версий.

**Проблема 7 — зависимость от LLM-оценщика.**

Если сама языковая модель оценивает свои предположения, это не является независимой проверкой.

> Поэтому для важных экспериментов необходимы контролируемые данные и независимые критерии оценки.

**Критерий завершения:** система сохраняет события и создаёт проверяемые ассоциативные связи.

### PHASE 2 — CONTEXTUAL MODEL

**Реализовать:**

- извлечение признаков контекста;
- модель вероятности ассоциации;
- оценку неопределённости;
- условную маршрутизацию.

**Критерий завершения:** одна и та же связь получает разные оценки в разных контекстах.

### PHASE 3 — BOUNDARY LEARNING

**Реализовать:**

- положительные свидетельства;
- отрицательные свидетельства;
- неопределённые результаты;
- обновление контекстных границ;
- защиту от ложных отрицательных выводов.

**Критерий завершения:** система способна учиться на валидных отрицательных проверках, не удаляя исходные воспоминания.

### PHASE 4 — ACTIVE PROBING

**Реализовать:**

- генерацию конкурирующих гипотез;
- выбор различающих контекстов;
- бюджет исследований;
- измерение информационного прироста.

**Критерий завершения:** система выбирает проверки, позволяющие различать заранее заданные объяснения.

### PHASE 5 — CONFLICT PRESERVATION

**Реализовать:**

- конфликтующие ветви;
- независимое хранение источников;
- историю текущих интерпретаций;
- механизм обновления позиции.

**Критерий завершения:** появление нового свидетельства не уничтожает исходные конфликтующие записи.

### PHASE 6 — EVALUATION

**Реализовать:**

- синтетический benchmark;
- базовые модели;
- абляционные тесты;
- метрики;
- воспроизводимый отчёт.

**Критерий завершения:** получены измеримые результаты, позволяющие сравнить FULL UROBOROS с базовыми версиями.

## 22. ФИНАЛЬНАЯ ФОРМУЛИРОВКА

UROBOROS_v1.0 — это экспериментальная архитектура внешней ассоциативной памяти, в которой отношения между воспоминаниями рассматриваются как **контекстно-зависимые гипотезы**, подлежащие проверке и последующему обновлению.

Её центральная особенность — сохранение не только положительных результатов ассоциативного извлечения, но и **отрицательных свидетельств**, ограничивающих область применимости конкретных связей.

Вместо бесконтрольного накопления ассоциаций система должна формировать проверяемую структуру:

- что было сохранено;
- с чем это связано;
- почему возникла предполагаемая связь;
- в каком контексте она проявилась;
- где она не подтвердилась;
- какие альтернативные объяснения существуют;
- насколько надёжна текущая интерпретация.

Таким образом, память становится не только хранилищем данных, но и **механизмом исследования собственных ассоциативных структур**.

### Главный принцип UROBOROS

```text
REMEMBER THE CONNECTION.
REMEMBER ITS CONDITIONS.
REMEMBER WHERE IT FAILS.
```

## APPENDIX B — СЛОВАРЬ

**TRACE** — исходная запись события с происхождением.

**ASSOCIATION** — отношение между двумя элементами памяти.

**POTENTIAL LINK** — предполагаемая, ещё не подтверждённая связь.

**CONTEXT** — набор обстоятельств, при которых оценивается ассоциация.

**BOUNDARY** — область условий, в которых связь считается применимой.

**POSITIVE TRACE** — свидетельство проявления связи.

**NEGATIVE TRACE** — свидетельство отсутствия ожидаемого проявления при валидной проверке.

**INCONCLUSIVE TRACE** — результат, недостаточный для обновления модели.

**ACTIVE PROBING** — выбор дополнительных условий для проверки гипотезы.

**INFORMATION GAIN** — уменьшение неопределённости после получения нового свидетельства.

**CONFLICT BRANCH** — отдельная сохранённая версия противоречивой информации.

**RETRIEVAL ROUTE** — путь извлечения воспоминания.

**PROVENANCE** — происхождение информации и история её получения.

# 24. HIERARCHICAL CONTEXTUAL ASSOCIATION MODEL

## 24.1. Иерархическая структура

В UROBOROS 2.0 применяется двухуровневая модель:

1. Глобальная модель ассоциаций.
2. Индивидуальная поправка конкретной пары воспоминаний.

Основное уравнение:

\[
z_{ij}(C)=
\theta_g^Tx(C)+
\Delta\theta_{ij}^Tx(C)
\]

Вероятность:

\[
p_{ij}(C)=\sigma(z_{ij}(C))
\]

Где:

- \(\theta_g\) — глобальные параметры;
- \(\Delta\theta_{ij}\) — парная поправка;
- \(x(C)\) — признаки текущего контекста;
- \(\sigma\) — логистическая функция.

Глобальная модель выявляет закономерности, общие для различных ассоциаций.

Парная поправка позволяет учитывать индивидуальные особенности конкретной связи.

## 24.2. Регуляризация парной модели

Для предотвращения переобучения на небольшом количестве свидетельств применяется зависимая от объёма данных регуляризация:

\[
\boxed{
\lambda_{ij}(n)=
\frac{\lambda_0}{1+n/m}
}
\]

Где:

- \(n\) — количество валидных свидетельств конкретной пары;
- \(\lambda_0\) — начальная сила регуляризации;
- \(m\) — параметр скорости её ослабления.

При небольшом количестве свидетельств индивидуальная поправка ограничена.

При накоплении новых проверенных данных её влияние постепенно возрастает.

Парная модель не должна получать чрезмерное влияние только из-за большого числа повторных или зависимых свидетельств.

## 24.3. Ансамблевая оценка

Для оценки применимости используется ансамбль из \(K\) участников.

Начальная конфигурация:

\[
K=20
\]

Каждый участник выдаёт собственную оценку:

\[
p_1(C),p_2(C),...,p_K(C)
\]

Ансамбль должен обладать реальным разнообразием обученных моделей.

Искусственное создание нескольких почти одинаковых прогнозов путём небольшого изменения одного среднего значения не считается полноценным ансамблевым обучением.

До реализации корректного bootstrap процедура синтетического ресемплинга отключается.

# 25. CONTEXT ENCODER & OBSERVABILITY

## 25.1. Представление контекста

Контекст определяется не только значениями признаков, но и доступностью наблюдений:

\[
C=(x,m)
\]

Где:

- \(x\) — вектор признаков;
- \(m\) — маска наблюдаемости.

Пример:

```python
Context = {
    "features": {
        "temporal_distance": 0.35,
        "semantic_similarity": 0.82,
        "environment_type": "technical"
    },
    "observability": {
        "temporal_distance": True,
        "semantic_similarity": True,
        "environment_type": True
    },
    "schema_version": "context-v1"
}
```

## 25.2. Отсутствующие данные

Отсутствие признака не должно автоматически преобразовываться в ноль.

\[
\boxed{MISSING\neq ZERO}
\]

Наблюдаемость должна учитываться при сравнении контекстов.

Если два контекста не имеют общих наблюдаемых признаков, их расстояние не определяется.

Такой случай должен возвращать неопределённость, а не искусственно минимальное расстояние.

## 25.3. Контекстное расстояние

Пусть \(J(C,C_n)\) — множество признаков, наблюдаемых в обоих контекстах.

Тогда:

\[
d^2(C,C_n)=
\frac{
\sum_{j\in J}w_jd_j^2(C,C_n)
}{
\sum_{j\in J}w_j
}
\]

Где:

- \(w_j\) — вес признака;
- \(d_j\) — функция расстояния, соответствующая типу признака.

Нормализация, типы признаков и веса фиксируются в версии Context Encoder.

# 26. MEMORY BOUNDARY LEARNING 2.0

## 26.1. Локальная поддержка контекста

Центральное уточнение MBL — использование локальной эффективной выборки.

Обычное общее количество свидетельств по паре не показывает, насколько хорошо изучен конкретный контекст.

Поэтому вводится контекстное ядро:

\[
\boxed{
a_n(C)=
\exp\left(
-\frac{d(C,C_n)^2}{2h^2}
\right)
}
\]

Где:

- \(C\) — проверяемый контекст;
- \(C_n\) — контекст ранее полученного свидетельства;
- \(d\) — контекстное расстояние;
- \(h\) — ширина ядра.

Локальная эффективная выборка:

\[
\boxed{
N_{\mathrm{eff}}(C)=
\frac{
\left(\sum_n a_n(C)\right)^2
}{
\sum_n a_n(C)^2
}
}
\]

В расчёт входят только валидные свидетельства с определённым расстоянием.

**Принципиальное отличие:** эффективная выборка рассчитывается относительно конкретного контекста, а не по всей истории ассоциации.

Большое количество свидетельств в одной области не гарантирует достаточную поддержку в другой.

Если пригодных свидетельств нет:

\[
N_{\mathrm{eff}}(C)=0
\]

## 26.2. Происхождение свидетельств

Повторение одного и того же первоисточника не должно создавать иллюзию независимого подтверждения.

Для этого используется `source_family` и отдельная структура `source_lineage`.

При этом исходная формула \(N_{\mathrm{eff}}(C)\) сохраняется.

Дополнительная оценка независимой поддержки, если она используется, рассчитывается отдельно и не подменяет основной показатель.

## 26.3. Квантильные границы ансамбля

Пусть ансамбль выдаёт набор прогнозов:

\[
P(C)=\{p_1(C),p_2(C),...,p_K(C)\}
\]

Рассчитываются:

\[
L_\alpha(C)=Q_\alpha(P(C))
\]

\[
U_\alpha(C)=Q_{1-\alpha}(P(C))
\]

Где \(Q\) — выбранный метод вычисления эмпирического квантиля.

Эти значения характеризуют распределение прогнозов ансамбля.

Они не должны автоматически интерпретироваться как статистические доверительные интервалы.

## 26.4. Три состояния границы

Вводятся три класса:

```text
B+ — CONFIRMED APPLICABILITY
B- — CONFIRMED NON-OBSERVATION
B? — UNKNOWN / INSUFFICIENT SUPPORT
```

Формальная классификация:

\[
\boxed{
B(C)=
\begin{cases}
B^+,&
L_\alpha(C)\geq\tau_+
\land N_{\mathrm{eff}}(C)\geq N_{\min}
\\
B^-,&
U_\alpha(C)\leq\tau_-
\land N_{\mathrm{eff}}(C)\geq N_{\min}
\\
B^?,&\text{otherwise}
\end{cases}
}
\]

Условия:

\[
0\leq\tau_-<\tau_+\leq1
\]

\[
0<\alpha<0.5
\]

\[
N_{\min}>0
\]

### B+ — подтверждённая применимость

Ассоциация имеет достаточную локальную поддержку, а нижняя граница ансамблевых прогнозов достигает положительного порога.

### B- — подтверждённое отсутствие проявления

Ассоциация не проявлялась в достаточно изученной области контекста.

Это не доказывает её универсальное отсутствие.

### B? — неопределённость

Недостаточно локальных свидетельств, наблюдается конфликт, разброс ансамбля слишком велик или отсутствуют необходимые данные.

**B? является полноценным результатом алгоритма, а не технической ошибкой.**

## 26.5. Параметры MBL

Параметры:

```python

    "alpha": 0.10,
    "tau_positive": 0.80,
    "tau_negative": 0.20,
    "n_min": 5,
    "kernel_width": 0.5,
    "quantile_method": "versioned"
}
```

Приведённые значения являются демонстрационной начальной конфигурацией, а не универсально установленными оптимальными параметрами.

Они должны подбираться на обучающей и калибровочной выборках.

# 28. ACTIVE CONTEXT PROBING 2.0

Выбор контекста для проверки должен учитывать не только информативность, но и стоимость, риск и практическую ценность.

\[
C^*=
\arg\max_{C\in\mathcal{C}_{allowed}}
\left[
IG(C)+\alpha T(C)-\lambda K(C)-\mu R(C)
\right]
\]

Где:

- \(IG\) — ожидаемый информационный прирост;
- \(T\) — ценность для текущей задачи;
- \(K\) — вычислительная стоимость;
- \(R\) — риск;
- \(\mathcal{C}_{allowed}\) — разрешённое множество контекстов.

Для вероятностного выбора применяется softmax:

\[
P(C_i|D)=
\frac{\exp(S(C_i)/T)}
{\sum_j\exp(S(C_j)/T)}
\]

Каждое решение сохраняет:

```python
ProbeDecision = {
    "candidate_set": [],
    "candidate_scores": {},
    "selection_probabilities": {},
    "selected_candidate": None,
    "selected_propensity": None,
    "temperature": None,
    "policy_version": None,
    "budget": None,
    "permissions": {}
}
```

Это необходимо для последующего анализа смещения отбора.

Ограничение обратных вероятностных весов снижает дисперсию оценки, но вносит смещение относительно несклиппированной IPW-оценки.

# 29. HCR — HONEST CONFLICT RESOLUTION

В UROBOROS 2.0 механизм сохранения противоречий дополняется последовательностью обработки конфликтов:

```text
DETECT
   ↓
PRESERVE
   ↓
VERIFY
   ↓
REASSESS
   ↓
DISCLOSE
   ↓
CONTINUE
```

### DETECT

Выявление несовместимых свидетельств и интерпретаций.

### PRESERVE

Сохранение всех значимых конфликтующих ветвей.

### VERIFY

Проверка источников, контекста и качества данных.

### REASSESS

Переоценка текущей интерпретации.

### DISCLOSE

Явное представление неопределённости и противоречий.

### CONTINUE

Продолжение исследования в рамках разрешений и бюджета.

Основные правила:

\[
SEARCH\neq CERTAINTY
\]

\[
UNRESOLVED\neq ABANDONED
\]

\[
UPDATE\ INTERPRETATION\neq REWRITE\ HISTORY
\]

История конфликтов должна быть append-only.

# 1. НАЗНАЧЕНИЕ И ГРАНИЦЫ ПРОТОТИПА

UROBOROS 2.0 — модульный экспериментальный слой контекстной ассоциативной памяти и обучения границ применимости (Memory Boundary Learning, MBL).

Основная задача системы — сохранять эпизоды и связи между ними, проверять поступающие свидетельства, оценивать локальную поддержку ассоциаций в конкретном контексте и выдавать консервативный статус применимости.

В отличие от простой системы поиска похожих воспоминаний, UROBOROS пытается разделять два вопроса:

- Существовала ли ассоциация между двумя объектами или событиями?
- Подтверждена ли применимость этой ассоциации в текущем контексте?

Это принципиально разные утверждения.

**UROBOROS 2.0 реализует:**

- четыре логических слоя памяти;
- неизменяемые исходные следы;
- граф ассоциативных связей;
- хранение потенциальных ассоциаций;
- проверку свидетельств `POSITIVE`, `NEGATIVE`, `INCONCLUSIVE`;
- сравнение контекстов с учётом наблюдаемости признаков;
- локальный Effective Sample Size (ESS);
- эмпирические квантильные границы ансамблевых оценок;
- три состояния применимости: `B+`, `B-`, `B?`;
- сохранение конфликтующих интерпретаций;

### TRACE MEMORY

Хранит исходные эпизоды, наблюдения, содержание и происхождение данных.

Основное правило:

`TRACE ≠ INTERPRETATION`

Исходный след не должен незаметно изменяться вследствие последующей переоценки.

В прототипе для таблицы следов используются SQLite-триггеры, блокирующие `UPDATE` и `DELETE`.

### ASSOCIATIVE MEMORY

Предназначена для хранения связей между эпизодами и объектами.

Ассоциация представляет собой гипотезу о связи, а не универсальное утверждение о применимости этой связи.

### POTENTIAL MEMORY

Хранит кандидатов ассоциаций, которые ещё не получили достаточного подтверждения.

Потенциальная связь не должна автоматически становиться подтверждённой.

### BOUNDARY MEMORY

Хранит результаты проверки применимости ассоциаций в конкретных контекстах.

Основные состояния:

- `B+` — подтверждённая применимость в исследованной области;
- `B-` — отсутствие проявления в исследованной области;
- `B?` — недостаточно данных для решения.

`B-` не означает универсальное доказательство отсутствия связи.

Изменение интерпретации не должно переписывать первоначальное наблюдение.

# 3. МАТЕМАТИЧЕСКАЯ МОДЕЛЬ

## 3.1. Контекстное ядро

Для текущего контекста \(C\) и сохранённого наблюдения \(C_n\) применяется гауссово ядро:

\[
a_n(C)=\exp\left(-\frac{d(C,C_n)^2}{2h^2}\right)
\]

Где:

- \(a_n(C)\) — вес наблюдения;
- \(d(C,C_n)\) — расстояние между контекстами;
- \(h\) — параметр ширины ядра.

Чем ближе контекст наблюдения к текущему запросу, тем выше его вес.

В реализации числовые признаки нормализуются относительно масштаба значений, категориальные сравниваются по совпадению.

Отсутствующие признаки не считаются нулевыми.

Если сопоставимых наблюдаемых признаков нет, расстояние считается неизвестным.

## 3.2. Локальный Effective Sample Size

\[
N_{\mathrm{eff}}(C)=
\frac{\left(\sum_n a_n(C)\right)^2}
{\sum_n a_n(C)^2}
\]

ESS оценивает эффективное количество наблюдений, поддерживающих оценку в локальной области контекста.

Важно: ESS рассчитывается относительно конкретного запроса, а не глобально для всей ассоциации.

**Дополнительная защита от ложной локальной поддержки:**

ESS инвариантен к общему масштабу весов. Поэтому даже большое количество очень далёких наблюдений может давать высокий ESS.

Для устранения этой проблемы система дополнительно проверяет абсолютную сумму весов:

\[
W(C)=\sum_n a_n(C)
\]

Для принятия решения должны одновременно выполняться два условия:

\[
N_{\mathrm{eff}}(C)\geq N_{\min}
\]

\[
W(C)\geq W_{\min}
\]

Если хотя бы одно условие не выполнено, система возвращает `B?`.

## 3.3. Ансамблевые квантильные границы

Для набора оценок ансамбля:

\[
P(C)=\{p_1(C),p_2(C),...,p_K(C)\}
\]

Вычисляются эмпирические квантили:

\[
L_\alpha(C)=Q_\alpha(P(C))
\]

\[
U_\alpha(C)=Q_{1-\alpha}(P(C))
\]

В текущей реализации применяется линейная интерполяция эмпирического квантиля.

Это не статистические доверительные интервалы.

Прототип получает оценки ансамбля от вызывающего кода. Он не обучает ансамбль самостоятельно и не создаёт независимое разнообразие моделей.

## 3.4. Правило определения границы

\[
B(C)=
\begin{cases}
B^+, & L_\alpha(C)\geq\tau_+
\land N_{\mathrm{eff}}(C)\geq N_{\min}
\land W(C)\geq W_{\min}\\
B^-, & U_\alpha(C)\leq\tau_-
\land N_{\mathrm{eff}}(C)\geq N_{\min}
\land W(C)\geq W_{\min}\\
B^?, & \text{иначе}
\end{cases}
\]

Где:

- \(\tau_+\) — положительный порог;
- \(\tau_-\) — отрицательный порог;
- \(N_{\min}\) — минимальный локальный ESS;
- \(W_{\min}\) — минимальная абсолютная масса весов;
- \(\alpha\) — уровень квантиля.

## 3.5. Активное зондирование контекста

Для выбора следующего контекста проверки используется функция полезности:

\[
S(C)=IG(C)+\alpha T(C)-\lambda K(C)-\mu R(C)
\]

Где:

- \(IG(C)\) — ожидаемый информационный выигрыш;
- \(T(C)\) — ценность задачи;
- \(K(C)\) — стоимость проверки;
- \(R(C)\) — риск;
- \(\alpha,\lambda,\mu\) — коэффициенты весов.

В текущем прототипе эти показатели передаются вызывающим кодом. Их нормализация и содержательная оценка должны быть определены экспериментальным протоколом.

Для стохастического выбора используется softmax:

\[
P(C_i\mid D)=
\frac{\exp(S(C_i)/T)}
{\sum_j\exp(S(C_j)/T)}
\]

Где \(T\) — температура выбора.

Система сохраняет вероятность выбора каждого кандидата (propensity).

Это позволяет в дальнейшем анализировать процедуру выбора контекстов. Однако данный механизм сам по себе ещё не является полноценной причинно-экспериментальной системой.

# 4. ПРОВЕРКА СВИДЕТЕЛЬСТВ И ГРАНИЧНЫЕ РЕШЕНИЯ

## 4.1. Три типа свидетельств

| Тип | Условие | Значение |
|---|---|---|
| `POSITIVE` | `outcome=True` | Положительное наблюдение |
| `NEGATIVE` | `outcome=False` | Отрицательное наблюдение |
| `INCONCLUSIVE` | `outcome=None` | Неопределённый результат |

`INCONCLUSIVE` не используется как положительное или отрицательное обучающее свидетельство.

## 4.2. Правила проверки

1. `POSITIVE` допустимо только при `outcome=True`.
2. `NEGATIVE` допустимо только при `outcome=False`.
3. `INCONCLUSIVE` допустимо только при `outcome=None` и `valid=False`.
4. Переданное вызывающим кодом `valid=True` само по себе не делает свидетельство валидным.
5. Проверяется наличие происхождения данных.
6. Проверяется факт наблюдения.
7. Проверяется успешность получения данных.
8. Проверяется полнота контекста.
9. Проверяется качество свидетельства.
10. Значения качества вне диапазона `[0,1]` отклоняются, а не автоматически обрезаются.

Оценка, сгенерированная самой языковой моделью, должна считаться `model_estimate`, а не независимым свидетельством.

Принадлежность нескольких источников к разным меткам не доказывает их статистическую независимость. Необходимо сохранять происхождение данных и возможные связи между источниками.

## 4.3. Honest Conflict Resolution

Протокол работы с конфликтами:

```text
DETECT
   |
   v
PRESERVE
   |
   v
VERIFY
   |
   v
REASSESS
   |
   v

   |
   v

```

Основные правила:

- обнаруживать противоречия;
- сохранять альтернативные интерпретации;
- не переписывать исходные следы;
- проверять происхождение свидетельств;
- пересматривать оценку при появлении новых данных;
- сообщать о неразрешённых конфликтах.

Ключевые принципы:

`SEARCH ≠ CERTAINTY`

## 8.5. `uroboros/context.py`

```python
from __future__ import annotations

import math

from .models import Context


def context_distance(a: Context, b: Context) -> float | None:
    """
    RMS distance over comparable observed features.

    Numeric features are scaled by max(1, |a|, |b|).
    Categorical values use 0/1 mismatch.

    Missing values are excluded, never imputed as zero.
    Returns None if there is no comparable overlap.
    """

    a_obs = a.observed_features()
    b_obs = b.observed_features()

    common = sorted(a_obs.intersection(b_obs))

    distances: list[float] = []

    for key in common:
        av = a.features.get(key)
        bv = b.features.get(key)

        if av is None or bv is None:
            continue

        if (
            isinstance(av, (int, float))
            and not isinstance(av, bool)
            and isinstance(bv, (int, float))
            and not isinstance(bv, bool)
        ):
            scale = max(
                1.0,
                abs(float(av)),
                abs(float(bv)),
            )

            distances.append(
                abs(float(av) - float(bv)) / scale
            )

        else:
            distances.append(
                0.0 if av == bv else 1.0
            )

    if not distances:
        return None

    return math.sqrt(
        sum(distance ** 2 for distance in distances)
        / len(distances)
    )


def gaussian_weight(
    distance: float,
    bandwidth: float,
) -> float:

    if bandwidth <= 0:
        raise ValueError("bandwidth must be > 0")

    return math.exp(
        -(distance ** 2) / (2.0 * bandwidth ** 2)
    )
```

```python
from .models import EvidenceInput, EvidenceKind


class EvidenceValidationError(ValueError):
    pass


def validate_evidence(
    item: EvidenceInput,
    min_quality: float = 0.5,
) -> None:

    if not 0.0 <= item.quality <= 1.0:
        raise EvidenceValidationError(
            "quality must be within [0, 1]"
        )

    if item.quality < min_quality:
        raise EvidenceValidationError(
            "quality below configured minimum"
        )

    if not item.source.strip():
        raise EvidenceValidationError(
            "source provenance is required"
        )

    if not item.observed:
        raise EvidenceValidationError(
            "outcome was not directly observed"
        )

    if not item.retrieval_succeeded:
        raise EvidenceValidationError(
            "retrieval/observation process failed"
        )

    if not item.context_complete:
        raise EvidenceValidationError(
            "context is incomplete"
        )

    if (
        item.kind is EvidenceKind.POSITIVE
        and item.outcome is not True
    ):
        raise EvidenceValidationError(
            "POSITIVE evidence requires outcome=True"
        )

    if (
        item.kind is EvidenceKind.NEGATIVE
        and item.outcome is not False
    ):
        raise EvidenceValidationError(
            "NEGATIVE evidence requires outcome=False"
        )

    if item.kind is EvidenceKind.INCONCLUSIVE:

        if item.outcome is not None:
            raise EvidenceValidationError(
                "INCONCLUSIVE evidence requires outcome=None"
            )

        if item.valid is True:
            raise EvidenceValidationError(
                "INCONCLUSIVE evidence cannot be marked valid"
            )

    # Caller-provided valid=True is deliberately
    # not sufficient to pass this validation gate.
```

## 8.7. `uroboros/boundary.py`

```python
from __future__ import annotations

from collections.abc import Sequence

from .context import (
    context_distance,
    gaussian_weight,
)

from .models import (
    Context,
    EvidenceRecord,
    EvidenceKind,
    BoundaryResult,
    BoundaryState,
)


def empirical_quantile(
    values: Sequence[float],
    q: float,
) -> float:

    if not values:
        raise ValueError("values cannot be empty")

    if not 0.0 <= q <= 1.0:
        raise ValueError("q must be within [0, 1]")

    xs = sorted(float(value) for value in values)

    if any(not 0.0 <= value <= 1.0 for value in xs):
        raise ValueError(
            "probabilities must be within [0, 1]"
        )

    # Linear interpolation:
    # common Type-7 sample quantile.

    h = (len(xs) - 1) * q

    lo = int(h)
    hi = min(lo + 1, len(xs) - 1)

    frac = h - lo

    return (
        xs[lo] * (1.0 - frac)
        + xs[hi] * frac
    )


def local_effective_sample_size(
    weights: Sequence[float],
) -> float:

    positive = [
        float(weight)
        for weight in weights
        if weight > 0.0
    ]

    if not positive:
        return 0.0

    numerator = sum(positive) ** 2

    denominator = sum(
        weight * weight
        for weight in positive
    )

    return (
        numerator / denominator
        if denominator
        else 0.0
    )


def evaluate_boundary(
    query: Context,
    evidence: Sequence[EvidenceRecord],
    ensemble_probabilities: Sequence[float],
    *,
    bandwidth: float = 0.35,
    alpha: float = 0.10,
    positive_threshold: float = 0.80,
    negative_threshold: float = 0.20,
    min_local_ess: float = 3.0,
    min_local_weight_sum: float = 1.0,
) -> BoundaryResult:

    if bandwidth <= 0:
        raise ValueError("bandwidth must be > 0")

    if not 0 < alpha < 0.5:
        raise ValueError(
            "alpha must be between 0 and 0.5"
        )

    if not (
        0 <= negative_threshold
        < positive_threshold
        <= 1
    ):
        raise ValueError(
            "require 0 <= negative_threshold "
            "< positive_threshold <= 1"
        )

    if min_local_ess <= 0:
        raise ValueError(
            "min_local_ess must be > 0"
        )

    probs = list(ensemble_probabilities)

    if not probs:
        return BoundaryResult(
            BoundaryState.UNKNOWN,
            None,
            None,
            0.0,
            0.0,
            0,
            "no ensemble predictions",
        )

    if any(not 0 <= p <= 1 for p in probs):
        raise ValueError(
            "ensemble probabilities must be within [0, 1]"
        )

    valid = [
        item
        for item in evidence
        if item.kind in (
            EvidenceKind.POSITIVE,
            EvidenceKind.NEGATIVE,
        )
    ]

    weights = []

    for item in valid:

        distance = context_distance(
            query,
            item.context,
        )

        if distance is not None:

            weights.append(
                gaussian_weight(
                    distance,
                    bandwidth,
                )
            )

    ess = local_effective_sample_size(weights)

    weight_sum = sum(weights)

    lower = empirical_quantile(
        probs,
        alpha,
    )

    upper = empirical_quantile(
        probs,
        1.0 - alpha,
    )

    # ESS alone is scale-invariant.
    # A large ESS can occur despite negligible
    # absolute kernel support.
    #
    # Therefore both ESS and absolute local
    # kernel mass are required.

    if (
        ess < min_local_ess
        or weight_sum < min_local_weight_sum
    ):

        return BoundaryResult(
            BoundaryState.UNKNOWN,
            lower,
            upper,
            ess,
            weight_sum,
            len(weights),
            "insufficient local evidence support or kernel mass",
        )

    if lower >= positive_threshold:

        return BoundaryResult(
            BoundaryState.POSITIVE,
            lower,
            upper,
            ess,
            weight_sum,
            len(weights),
            "lower empirical ensemble quantile exceeds positive threshold",
        )

    if upper <= negative_threshold:

        return BoundaryResult(
            BoundaryState.NEGATIVE,
            lower,
            upper,
            ess,
            weight_sum,
            len(weights),
            "upper empirical ensemble quantile is below negative threshold",
        )

    return BoundaryResult(
        BoundaryState.UNKNOWN,
        lower,
        upper,
        ess,
        weight_sum,
        len(weights),
        "ensemble bounds do not establish a boundary",
    )
```

## 8.8. `uroboros/database.py`

```python
from __future__ import annotations

import json
import sqlite3

from .models import (
    Context,
    EvidenceRecord,
    EvidenceKind,
    TraceRecord,
    new_id,
)


SCHEMA = """
PRAGMA foreign_keys = ON;

CREATE TABLE IF NOT EXISTS traces (
    trace_id TEXT PRIMARY KEY,
    content TEXT NOT NULL,
    context_json TEXT NOT NULL,
    source TEXT NOT NULL,
    created_at REAL NOT NULL
);

CREATE TRIGGER IF NOT EXISTS traces_no_update
BEFORE UPDATE ON traces
BEGIN
    SELECT RAISE(
        ABORT,
        'trace records are immutable'
    );
END;

CREATE TRIGGER IF NOT EXISTS traces_no_delete
BEFORE DELETE ON traces
BEGIN
    SELECT RAISE(
        ABORT,
        'trace records are immutable'
    );
END;

CREATE TABLE IF NOT EXISTS associations (
    association_id TEXT PRIMARY KEY,
    created_at REAL NOT NULL
);

CREATE TABLE IF NOT EXISTS potential_associations (
    association_id TEXT PRIMARY KEY,
    source_trace_id TEXT NOT NULL,
    target_trace_id TEXT NOT NULL,
    score REAL NOT NULL,
    status TEXT NOT NULL,
    note TEXT NOT NULL,
    created_at REAL NOT NULL,

    FOREIGN KEY(source_trace_id)
        REFERENCES traces(trace_id),

    FOREIGN KEY(target_trace_id)
        REFERENCES traces(trace_id)
);

CREATE TABLE IF NOT EXISTS evidence (
    evidence_id TEXT PRIMARY KEY,
    association_id TEXT NOT NULL,
    context_json TEXT NOT NULL,
    kind TEXT NOT NULL,
    outcome INTEGER,
    quality REAL NOT NULL,
    source TEXT NOT NULL,
    source_family TEXT,
    created_at REAL NOT NULL,

    FOREIGN KEY(association_id)
        REFERENCES associations(association_id)
);

CREATE TABLE IF NOT EXISTS conflict_branches (
    branch_id TEXT PRIMARY KEY,
    subject_id TEXT NOT NULL,
    interpretation TEXT NOT NULL,
    status TEXT NOT NULL,
    source TEXT NOT NULL,
    created_at REAL NOT NULL
);

CREATE TABLE IF NOT EXISTS probe_logs (
    log_id TEXT PRIMARY KEY,
    context_id TEXT NOT NULL,
    score REAL NOT NULL,
    propensity REAL NOT NULL,
    policy_version TEXT NOT NULL,
    temperature REAL NOT NULL,
    candidate_set_json TEXT NOT NULL,
    created_at REAL NOT NULL
);
"""


class MemoryDB:

    def __init__(
        self,
        path: str = "uroboros.sqlite3",
    ):

        self.conn = sqlite3.connect(path)

        self.conn.row_factory = sqlite3.Row

        self.conn.executescript(SCHEMA)

    def close(self):
        self.conn.close()

    @staticmethod
    def _context_json(
        context: Context,
    ) -> str:

        return json.dumps(
            {
                "features": dict(context.features),
                "observed": sorted(
                    context.observed_features()
                ),
            },
            sort_keys=True,
        )

    @staticmethod
    def _context_from_json(
        payload: str,
    ) -> Context:

        data = json.loads(payload)

        if (
            isinstance(data, dict)
            and "features" in data
        ):

            return Context(
                data["features"],
                frozenset(
                    data.get("observed", [])
                ),
            )

        # Backward compatibility
        # with early scaffold files.

        return Context(data)

    def add_trace(
        self,
        trace: TraceRecord,
    ) -> None:

        self.conn.execute(
            """
            INSERT INTO traces
            VALUES (?, ?, ?, ?, ?)
            """,
            (
                trace.trace_id,
                trace.content,
                self._context_json(trace.context),
                trace.source,
                trace.created_at,
            ),
        )

        self.conn.commit()

    def ensure_association(
        self,
        association_id: str,
        created_at: float,
    ) -> None:

        self.conn.execute(
            """
            INSERT OR IGNORE INTO associations
            VALUES (?, ?)
            """,
            (
                association_id,
                created_at,
            ),
        )

        self.conn.commit()

    def add_evidence(
        self,
        item: EvidenceRecord,
    ) -> None:

        self.ensure_association(
            item.association_id,
            item.created_at,
        )

        self.conn.execute(
            """
            INSERT INTO evidence
            VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?)
            """,
            (
                item.evidence_id,
                item.association_id,
                self._context_json(item.context),
                item.kind.value,
                (
                    None
                    if item.outcome is None
                    else int(item.outcome)
                ),
                item.quality,
                item.source,
                item.source_family,
                item.created_at,
            ),
        )

        self.conn.commit()

    def get_evidence(
        self,
        association_id: str,
    ) -> list[EvidenceRecord]:

        rows = self.conn.execute(
            """
            SELECT *
            FROM evidence
            WHERE association_id=?
            ORDER BY created_at
            """,
            (association_id,),
        ).fetchall()

        return [
            EvidenceRecord(
                evidence_id=row["evidence_id"],
                association_id=row["association_id"],
                context=self._context_from_json(
                    row["context_json"]
                ),
                kind=EvidenceKind(row["kind"]),
                outcome=(
                    None
                    if row["outcome"] is None
                    else bool(row["outcome"])
                ),
                quality=row["quality"],
                source=row["source"],
                source_family=row["source_family"],
                created_at=row["created_at"],
            )
            for row in rows
        ]

    def add_potential_association(
        self,
        item,
    ) -> None:

        if not 0.0 <= item.score <= 1.0:
            raise ValueError(
                "potential association score must be within [0, 1]"
            )

        self.conn.execute(
            """
            INSERT INTO potential_associations
            VALUES (?, ?, ?, ?, ?, ?, strftime('%s','now'))
            """,
            (
                item.association_id,
                item.source_trace_id,
                item.target_trace_id,
                item.score,
                item.status,
                item.note,
            ),
        )

        self.conn.commit()

    def list_potential_associations(self):

        return self.conn.execute(
            """
            SELECT *
            FROM potential_associations
            ORDER BY created_at DESC
            """
        ).fetchall()

    def add_conflict_branch(
        self,
        subject_id: str,
        interpretation: str,
        source: str,
        status: str = "OPEN",
    ) -> str:

        branch_id = new_id()

        self.conn.execute(
            """
            INSERT INTO conflict_branches
            VALUES (?, ?, ?, ?, ?, strftime('%s','now'))
            """,
            (
                branch_id,
                subject_id,
                interpretation,
                status,
                source,
            ),
        )

        self.conn.commit()

        return branch_id

    def list_conflict_branches(
        self,
        subject_id: str,
    ):

        return self.conn.execute(
            """
            SELECT *
            FROM conflict_branches
            WHERE subject_id=?
            ORDER BY created_at
            """,
            (subject_id,),
        ).fetchall()

    def log_probe(
        self,
        decision,
        candidate_set,
    ) -> None:

        self.conn.execute(
            """
            INSERT INTO probe_logs
            VALUES (?, ?, ?, ?, ?, ?, ?, strftime('%s','now'))
            """,
            (
                new_id(),
                decision.context_id,
                decision.score,
                decision.propensity,
                decision.policy_version,
                decision.temperature,
                json.dumps(
                    candidate_set,
                    sort_keys=True,
                ),
            ),
        )

        self.conn.commit()
```

## 8.9. `uroboros/probing.py`

```python
from __future__ import annotations

import math
import random

from .models import (
    ProbeCandidate,
    ProbeDecision,
)


def choose_context(
    candidates: list[ProbeCandidate],
    *,
    alpha: float = 1.0,
    cost_weight: float = 1.0,
    risk_weight: float = 1.0,
    temperature: float = 0.25,
    policy_version: str = "softmax-v1",
    rng: random.Random | None = None,
) -> tuple[ProbeDecision, list[dict]]:

    if not candidates:
        raise ValueError(
            "at least one allowed candidate is required"
        )

    if temperature <= 0:
        raise ValueError(
            "temperature must be > 0"
        )

    for candidate in candidates:

        if min(
            candidate.information_gain,
            candidate.task_value,
            candidate.cost,
            candidate.risk,
        ) < 0:

            raise ValueError(
                "candidate values must be non-negative"
            )

    # Callers must normalize inputs consistently
    # and log the candidate set and policy version.

    scores = {
        candidate.context_id:
            candidate.information_gain
            + alpha * candidate.task_value
            - cost_weight * candidate.cost
            - risk_weight * candidate.risk

        for candidate in candidates
    }

    max_score = max(scores.values())

    exps = {
        key: math.exp(
            (value - max_score) / temperature
        )
        for key, value in scores.items()
    }

    total = sum(exps.values())

    probs = {
        key: value / total
        for key, value in exps.items()
    }

    chooser = rng or random.Random()

    ids = list(probs)

    chosen = chooser.choices(
        ids,
        weights=[probs[key] for key in ids],
        k=1,
    )[0]

    decision = ProbeDecision(
        chosen,
        scores[chosen],
        probs[chosen],
        policy_version,
        temperature,
    )

    log = [
        {
            "context_id": candidate.context_id,
            "score": scores[candidate.context_id],
            "propensity": probs[candidate.context_id],
        }
        for candidate in candidates
    ]

    return decision, log
```

## 8.10. `uroboros/conflicts.py`

```python
from __future__ import annotations

from .database import MemoryDB


class HonestConflictResolution:
    """
    HCR:
    DETECT -> PRESERVE -> VERIFY
    -> REASSESS -> DISCLOSE -> CONTINUE
    """

    def __init__(
        self,
        db: MemoryDB,
    ):

        self.db = db

    def preserve(
        self,
        subject_id: str,
        interpretations: list[tuple[str, str]],
    ) -> list[str]:

        if not interpretations:
            raise ValueError(
                "at least one interpretation is required"
            )

        # Append-only:
        # competing interpretations are never
        # silently overwritten.

        return [
            self.db.add_conflict_branch(
                subject_id,
                text,
                source,
                "OPEN",
            )
            for text, source in interpretations
        ]

    def branches(
        self,
        subject_id: str,
    ):

        return self.db.list_conflict_branches(
            subject_id
        )
```

```python
        trace = TraceRecord(
            new_id(),

            Context(context),
            source,

    def add_potential_association(
        self,
        source_trace_id: str,
        target_trace_id: str,
        score: float,
        note: str = "",
        status: str = "CANDIDATE",
    ):

        item = PotentialAssociation(
            new_id(),
            source_trace_id,
            target_trace_id,
            score,
            status,
            note,
        )

        self.db.add_potential_association(
            item
        )

        return item

    def record_evidence(
        self,
        item: EvidenceInput,
    ) -> EvidenceRecord:

        validate_evidence(
            item,
            self.min_quality,
        )

        record = EvidenceRecord(
            evidence_id=new_id(),
            association_id=item.association_id,
            context=item.context,
            kind=item.kind,
            outcome=item.outcome,
            quality=item.quality,
            source=item.source,
            source_family=item.source_family,
        )

        self.db.add_evidence(record)

        return record

    def evaluate(
        self,
        association_id: str,
        query_context: Context,
        ensemble_probabilities: list[float],
        **kwargs,
    ):

        evidence = self.db.get_evidence(
            association_id
        )

        return evaluate_boundary(
            query_context,
            evidence,
            ensemble_probabilities,
            **kwargs,
        )

    def select_probe(
        self,
        candidates,
        **kwargs,
    ):

        decision, candidate_log = choose_context(
            candidates,
            **kwargs,
        )

        self.db.log_probe(
            decision,
            candidate_log,
        )

        return decision, candidate_log
```

# 10. ОГРАНИЧЕНИЯ ТЕКУЩЕЙ РЕАЛИЗАЦИИ

Текущий прототип является работающим модульным программным каркасом, но не завершённой исследовательской системой.

Следующие компоненты пока не реализованы как полноценные механизмы:

- обучение глобальной модели;
- pair-specific коррекция с shrinkage;
- полноценный ансамбль из 20 действительно различающихся участников;
- автоматическое формирование независимых ансамблевых оценок;
- калибровка вероятностей;
- отдельная калибровка неопределённости и квантилей;
- полноценный генератор кандидатов ассоциаций с отдельным вычислительным лимитом;
- законченный причинно-экспериментальный контур active probing;
- benchmark против альтернативных методов;
- независимая внешняя оценка качества и обобщения.

Наличие интерфейса для передачи ансамблевых вероятностей не означает, что сам ансамбль уже обучен или реализован.

Наличие функции выбора контекста не означает, что система самостоятельно умеет определять истинный информационный выигрыш, риск или стоимость проверки.

Эти показатели должны быть операционализированы и проверены отдельно.

# 11. ДАЛЬНЕЙШЕЕ РАЗВИТИЕ

Рекомендуемая последовательность разработки UROBOROS 2.0:

**Этап 1 — стабилизация ядра**

- зафиксировать формат данных;
- добавить версии схемы SQLite;
- реализовать миграции;
- расширить проверки входных данных;
- добавить интеграционные тесты.

**Этап 2 — MBL Engine**

- реализовать глобальную модель;
- добавить pair-specific correction;
- использовать shrinkage для стабилизации малых выборок;
- отделить глобальную закономерность от локальной применимости.

**Этап 3 — ансамблевая оценка**

- реализовать ансамбль из нескольких моделей;
- документировать процедуру получения разнообразия;
- проверить корреляцию ошибок участников;
- отделить разброс ансамбля от статистической неопределённости.

**Этап 4 — калибровка**

- реализовать калибровку вероятностей;
- отдельно исследовать калибровку неопределённости;
- проверить эмпирические квантильные границы;
- фиксировать калибровочные и тестовые выборки.

**Этап 5 — Active Context Probing**

- реализовать генератор допустимых контекстов;
- ввести ограничения бюджета;
- фиксировать полный набор кандидатов;
- сохранять оценки, вероятности выбора и версию политики;
- исследовать влияние propensity на оценку результатов.

**Этап 6 — экспериментальная проверка**

- создать синтетический benchmark;
- добавить реальные контролируемые сценарии;
- сравнить систему с обычным retrieval;
- сравнить global-only и pair-specific подходы;
- провести ablation-тесты;
- опубликовать результаты и ограничения.

# 12. ВОСПРОИЗВОДИМОСТЬ И НАУЧНАЯ ОСТОРОЖНОСТЬ

До начала эксперимента необходимо зафиксировать:

- ширину контекстного ядра `h`;
- уровень квантилей `alpha`;
- положительный и отрицательный пороги;
- минимальный local ESS;
- минимальную массу локальных весов;
- версию модели или ансамбля;
- правила отбора свидетельств;
- правила исключения невалидных наблюдений;
- процедуру калибровки;
- версию программного кода.

Настройка параметров должна проводиться на обучающей или калибровочной выборке, но не на тестовой.

Необходимо сохранять исходные наблюдения, контекст, происхождение данных, версию политики и параметры запуска.

Нельзя смешивать независимость источников с принадлежностью к разным меткам: два разных источника могут происходить из одной первичной записи.

Нельзя интерпретировать `B-` как универсальное отрицание.

Нельзя считать разброс ансамбля автоматически откалиброванной неопределённостью.

Нельзя считать высокую воспроизводимость результата в нескольких языковых моделях доказательством субъективного опыта или сознания.

**Научная граница проекта:**

UROBOROS исследует наблюдаемое поведение системы:

`OPERATOR — LLM — CONTEXT — TECHNICAL ENVIRONMENT`

Архитектура не доказывает наличие сознания, субъективного опыта или биологической эквивалентности у языковой модели.

Её задача — исследовать контекстную применимость ассоциаций, сохранение истории, обработку противоречий и границы обоснованности выводов.
